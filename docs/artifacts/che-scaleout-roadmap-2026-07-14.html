Consistent-Hash Exchange Scale-Out — Roadmap

How hoppity will offer partitioned, ordered, horizontally-scaled consumption over a RabbitMQ consistent-hash exchange (CHE).

Status: planning · 2026-07-14

TL;DR

CHE scale-out ships as opt-in add-ons, not core. There are two viable patterns — B (per-instance queues) and C (fixed queues + coordinated assignment) — with materially different trade-offs around durability and infrastructure. A hoppity user would rationally choose either depending on their needs, so hoppity offers both rather than picking for them.

Order of work: build B first (no external dependencies), then C (requires a coordinator). Separate efforts.

The core insight: where does rebalancing live?

A CHE routes key → queue. Preserving per-key ordering and affinity requires one consumer per queue. But RabbitMQ has no native consumer-group assignment — nothing decides which instance owns which queue, or reshuffles when instances come and go. The two approaches are simply different answers to "who owns rebalancing?"

Approach B — RabbitMQ's hash ring owns it

key → CHE ring → per-instance queue → that instance

Each instance declares its own queue. Adding/removing an instance changes the ring; ~1/N of keys migrate automatically. No coordinator — the broker is the coordinator.

Approach C — your coordinator owns it

key → CHE ring → fixed queue → assigned instance

Fixed durable queues; a coordinator assigns each instance a disjoint subset and reshuffles on membership change. The queue is decoupled from any instance's lifecycle.

This single difference drives every trade-off below. B pushes rebalancing into the broker (simple, but the queue lives and dies with its instance). C keeps it in your app (durable and loss-free, but you run the machinery RabbitMQ won't give you).

The two add-ons

Add-on B · build first

Per-instance queues

Each service instance declares its own queue(s) bound to the CHE. The ring spreads keys across instances; scaling out = more queues = more throughput. Actor affinity falls out naturally: customerId → one queue → one instance.

  • No external dependencies — the hash ring handles distribution and failover
  • Automatic rebalance on scale/deploy/crash (~1/N keys migrate)
  • Simplest operational model; closest to the classic CHE pattern
  • Ephemeral queues → in-flight message loss when an instance dies ungracefully
  • Ring churns on every membership change (accepted consistent-hash cost)
  • Brief ordering hiccup for a key while it migrates across the remap
Internal fork — durability vs availability Ephemeral (exclusive/auto-delete): failover, but lose the dead queue's messages. Stable-durable (ordinal names, e.g. StatefulSet): no loss on crash (pod reclaims its queue), but that key-slice stalls while the pod is down + orphans on scale-down. Pick as part of B's design.

Best for: actor workloads where state rehydrates or an upstream outbox/retry re-drives dropped messages; teams that want zero coordination infra.

Add-on C · build second

Fixed queues + coordinated subset assignment

A fixed set of N durable queues. Each instance consumes a disjoint subset; a coordinator assigns and rebalances. Over-partition (N > instances) so subsets divide cleanly and there's headroom to scale.

  • Durable, stable queues → no message loss (un-acked requeue, queue reassigned to a live instance)
  • True failover without loss — the consumer moves, not the queue
  • Queue identity independent of instance lifecycle
  • Needs coordination RabbitMQ won't provide — external dependency by design
  • More moving parts; rebalance = stop-assign-resume across consumers
Two assignment strategies Static / ordinal: instance i of m owns queues where idx % m == i (StatefulSet ordinal; Kafka "static membership"). You supply i+m. Dynamic / coordinated: a leader assigns & rebalances (Rebalanser-style: lease-elected coordinator over a DB/consensus backend). Start static; add dynamic only if needed.

Best for: no-loss requirements, stable partitions, teams fine with running (or depending on) a coordinator. External deps are an accepted, eyes-open cost of choosing C.

Sequencing

  1. Add-on B — per-instance queues. Simpler, no external deps. Decide the ephemeral-vs-stable fork as part of its design.
  2. Add-on C — fixed queues + subset assignment. Start with static/ordinal assignment; reach for a dynamic coordinator only if the ordinal model proves insufficient.
